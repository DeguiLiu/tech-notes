1结论速览

四个问题，先给结论，后面逐条展开。
Q1 · PySide6 是真正的多线程吗？
是。 Qt 的 QThread 是对原生线程的直接封装，每一个都是操作系统级线程，不是协程/绿色线程。线程是「真的」，但代码跑不跑得动是另一回事——见 Q2。
Q2 · 受 Python「假多线程」影响吗？
纯 Python 的 CPU 计算受 GIL 串行化；但 numpy / ctypes 调 C++ / 共享内存读写会释放 GIL，这里才是真正并行。本工程把重计算都放进了释放 GIL 的路径，靠架构绕开了假多线程。
Q3 · 视频播放窗口是单独线程吗？
实时画面：不是——QOpenGLWidget 活在 GUI 线程，靠 QTimer 轮询 + 零拷贝喂帧。
视频回放：是——_DecodeThread(QThread) 在后台解码。Qt 的硬约束：所有控件必须活在 GUI 线程（Qt 控件非线程安全）。
Q4 · 如何支持 1920×1440 @ 30fps？
一帧 Y16 = 5.5 MB ≈ 166 MB/s ——靠 全程零拷贝（共享内存 numpy 视图 → glTexSubImage2D 直传）+ QTimer 过采样快进（丢中间帧）。重计算在生产者线程，GUI 线程只做「读最新 + 上传 + 画」。

2基础：真正的线程，但 Python 有 GIL

Qt/Qt 线程是货真价实的原生线程。 QThread 底层就是 CreateThread / pthread_create，一个线程一个内核调度实体。 但 PySide6 里跑的是 Python 字节码，而 CPython 解释器全局有一把 GIL（全局解释器锁）： 同一时刻只有一个线程能执行 Python 字节码——这就是「假多线程」的由来。

场景是否真正并行说明
两个线程同时跑纯 Python 循环（如字符串处理）否GIL 在 sys.setswitchinterval（默认 5ms）内轮转，等于分时，多核吃不满。
numpy 重数组运算是numpy 底层是 C，进入 C 后释放 GIL，可以和其他线程并行。
ctypes 调 C/C++（本工程 hcs_core 的 C ABI）是ctypes 调用期间释放 GIL（CLAUDE.md E4 明确要求耗时调用放锁，避免卡 GUI）。
共享内存原子头尾指针读写是一次 u32 原子 load，微秒级，不碰 GIL。
Qt 信号跨线程投递是队列连接（QueuedConnection）由事件循环投递，本身是原生线程间通信。
「放 GIL 真并行」到底指什么
GIL 的规则是：同一时刻，整个进程只有一个线程在执行 Python 字节码。所以两个线程都在跑纯 Python 时， 即使有两个核，也只有一个核在动——这是「假多线程」。但只要某个线程 进入会释放 GIL 的代码（numpy 运算、 ctypes 调 C/C++、I/O、Qt 事件循环），锁就暂时松开，另一个线程可以抢到 GIL 跑自己的字节码——这一刻两个线程在 不同的核上真并行。GIL 锁的是 Python 字节码，不锁 C。

61920×1440 @ 30fps 是怎么做到的

先算账：一帧 Y16 = 1920 × 1440 × 2B ≈ 5.5 MB；30fps 就是持续 ≈ 166 MB/s 的数据流。 为什么一个小应用扛得住？不是靠「快」，而是靠 几乎不拷贝。
环节是否拷贝方式
生产者合成帧 → 共享内存写入一次生产者把帧写进 FrameChannel 槽位，只有这一次实际写内存
共享内存 → Python零拷贝np.frombuffer(memoryview) 直接包住共享段，不 memcpy
Python → GUI 消费者零拷贝传 numpy 视图引用（保持 base 引用，避免悬垂）

三个关键设计：
  • QTimer 过采样 + 快进。 消费轮询按 帧周期 ÷ 4（30fps → ~125Hz）过采样，read_latest() 有「无新帧」快速路径（一次 u32 load）；有新帧就直接跳到最新，丢中间帧不排队——GUI 线程永远没有积压。
  • 重计算全在生产者线程。 帧合成（numpy）不在 GUI 线程；GUI 线程每帧只做「原子读 + 上传 + 画」，每步都是微秒级。
  • GPU 分担上色。 伪彩映射放在片段着色器（GPU），CPU 不做任何逐像素转换——把最贵的像素活交给显卡。

6.1 复合帧：图像与信息行必须共享 frame_id
本工程的一帧是复合帧：1920×1440 图像 + 信息行（温度、状态、checksum）。 最常见的 bug 是「GUI 拉一帧、统计延迟两秒、结果贴错帧」——所以图像和温度必须用同一个 frame_id 对齐。
  • 同 token 对齐。 image / infoline / metadata 放在同一个 token（frame_id + generation）上，消费者按 frame_id 校验代际。
  • 旧结果不覆盖新帧。 迟到的旧 frame_id 结果直接拒绝，不能覆盖新帧的温度显示。
  • 解析失败不猜。 信息行校验失败只标记 metadata_error，图像仍可显示——但绝不「猜温度」。
6.2 为什么上色用 RG8 而不是 R16
GL_R16 / GL_R16UI 是 16-bit 单通道纹理最干净的接口，但实测在多个 Intel 驱动下上传后屏幕全黑。 所以改为 GL_RG8 + GL_UNSIGNED_BYTE：把 little-endian Y16 的低字节 → R、高字节 → G，片段着色器内重建 16-bit 再查伪彩 LUT——这条路在 Intel / NVIDIA / AMD 都能跑。
  • PBO 不是可选项。 PySide6 6.x 的 glTexSubImage2D 绑定层对 pixels 参数只接受 buffer 对象；None / 0 / c_void_p(0) 会被拒绝或崩溃。出货路径就是 glTexSubImage2D 直传，首次使用即永久回落。
  • CPU fallback 不能当性能验收路径。 必须单独记录帧率与 P95/P99，不能用它证明 GPU 路径预算达标。

7零拷贝的底层：共享内存 + C 内存布局契约

零拷贝不是「两种语言的数据结构互相兼容」，而是：双方都不传对象，改共享同一块内存、按同一份字节布局去解释它。 §6 那张「唯一一次 DMA」表的根因就在这里。
7.1 跨语言边界只认「裸内存 + 布局契约」
Python 的 dict、C++ 的 std::vector 互不兼容——但零拷贝路径上根本不传这些对象。 传的是一段共享内存的地址（Windows 命名 section osp_fc_sim），两边各自按同一份二进制布局读写。 这份布局契约就是 C ABI（frame_channel.hpp ↔ frame_channel.py）。 
// frame_channel.hpp —— 结构体就长在共享内存里
struct FrameSlotHeader {
    uint32_t magic;      // 0x48534C54 'HSLT'
    uint32_t frame_no;
    uint32_t width, height;
    uint32_t dtype;      // 0=u8 1=u16 2=f32 3=f64
    uint32_t payload_size, crc32, committed;
};  // 到 64 字节，布局与 Python 契约一致
C++ 侧：struct 定义就是内存布局，直接写。
# frame_channel.py —— 同一份字节布局
SLOT_HEADER_FORMAT = "<16I"   # 小端 16×u32

7.2 兼容什么、不兼容什么
「数据结构兼容」实际指的是：numpy 数组 ↔ C 连续数组天生同构。numpy 默认内存排布就是 C-contiguous 行主序， 和 C/C++ 的 uint16_t frame[w*h] 逐字节一致；再加上小端序 = x86/x64 原生字节序（同机直接读）。
类型能否走零拷贝说明
numpy 数组 ↔ C 连续数组（定长）兼容C-contiguous、行主序、固定宽度类型，直接 np.frombuffer 共享。
POD 结构体（全部固定宽度字段）兼容无虚表、无字符串、无内嵌指针，用 struct 按偏移读写。
Python 对象（dict / list / int）不兼容含对象头/引用，必须序列化再传输。
C++ std::vector / std::string不兼容栈上只有指针，数据在堆上，跨语言无法直接读。
C++ class（含 vtable / 内部布局）不兼容布局未定义，不能跨语言解释。
7.3 「Python 和 C++ 都是读写 C 内存结构？」—— 是，但方式不同
跨语言边界上，C++ 直接写 C 结构体进共享内存（它的 struct 定义就是内存布局本身，无中间层）； Python 用 struct + numpy 按偏移解释同一段字节——等价于逐字段读 C 结构体，只是没有「C 结构体」这种语言原生结构。

7.4 跨语言硬约束 E1–E5
整套零拷贝能否成立，取决于五条跨语言硬约束不被破坏——任何一条被打破，前面所有优化立刻失效。
约束内容违背后果
E1numpy 视图生命周期不得超过 C++ 共享段 + slot lease悬垂访问 / UAF / 撕裂
E2ctypes 结构体宽度 / packing / 常量集中定义，配 ABI 测试跨语言布局错位
E3C++ 内存只走 C ABI 原子 / FrameChannel 头尾，Python Lock 不能保护 C++ SHM锁语义错配，跨语言不成立
E4昂贵 native 调用必须释放 GIL，且不能从 Qt GUI 线程调用GUI 线程卡顿
E5中断 / 半初始化 / 拔插 / 重复 close 是正常输入，清理必须幂等句柄 / SHM / 视图残留
一句话E1 / E3 是零拷贝契约的底线，E4 是线程拓扑成立的前提，E5 是拔插、崩溃下仍然稳定的根因。
