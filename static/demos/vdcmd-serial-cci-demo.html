命令传输的多物理通道：UART 与 I2C 如何承载同一套命令

同一套控制命令，既可以从串口进来，也可以从I2C 命令信箱进来，还能从SPI 从机进来。三条物理通道各有各的帧格式与调度方式，但最终都收敛到同一个共享命令解析器——理解"多通道、单解析器"这一约束，是读懂一切命令交互逻辑的前提。

1为什么需要多通道

设备往往同时挂在多种主机生态里：PC 通过串口调试与升级，传感器侧主控通过 I2C做寄存器级控制，板级主控通过 SPI下发批量命令。为每类宿主提供对应的物理入口，可以解耦集成方式、隔离故障域，也允许不同板卡只启用其中部分通道。

通道典型主机帧形态调度模型
UARTPC / 上位机同步字 + 长度 + payload + 校验共享命令事件线程
I2C（命令信箱）传感器侧主控从机地址 + 寄存器信箱共享命令事件线程
SPI板级主控header + payload + response独立 IO/Proc 线程
关键约束：多入口 ≠ 多命令状态机。三通道共享同一个命令解析器与唯一忙态，同一时刻只有一条命令在执行；其余请求收到忙态拒绝后等待重试。

2UART 帧：同步字、长度、payload 与校验

UART 命令帧用同步字 + 长度 + payload + 校验四段组织：同步字标记帧起点并帮助检测半包，长度字段界定 payload 边界，payload 承载命令 ID 与参数，校验字段保证帧的完整性。

帧 = 同步字 + 长度 + payload + 校验
  · 同步字  识别帧起点，发现半包 / 错位
  · 长度    界定 payload 边界
  · payload 命令 ID 与参数字节
  · 校验    CRC / 校验和，防错帧

主机按帧格式逐字节写入，设备端 RX 中断只投递"收到数据"事件，真正的读 FIFO、状态机组帧与调用解析器都发生在命令线程；结果经 TX 原路回发。

坑：RX 回调不解析帧内容——中断里只做最少工作，把组帧与校验留在命令线程，避免中断过长与状态被并发破坏。

3I2C 帧：从机地址、寄存器信箱与状态

I2C 场景下设备是从机。主控按从机地址 + 寄存器偏移发起写事务，把命令写进设备侧的命令信箱寄存器；命令执行完成后设备写完成状态位，主控轮询状态再读取结果。

I2C 写事务 = 从机地址 + 寄存器偏移 + 命令分块
  · 命令信箱  按寄存器分块保存命令
  · 完成状态  执行结果位，主控轮询
  · 读事务    主控按偏移读回结果缓冲

与 UART 的"主动回发"不同，I2C 单次事务长度有限，命令按信箱分块；交接靠状态位而非推送。

边界：完成状态位、结果缓冲与命令信箱是三块独立寄存器；读结果前必须先确认状态位有效，否则可能读到半成品。

4SPI：从机事务与独立线程调度

SPI 场景下设备是从机。主控分阶段发送 header 与 payload，设备由独立 IO/Proc 线程接管：IO 线程收数据并投递 SPI 命令事件，处理线程组帧、调用共享解析器，再组装 response 交回 IO 发送。

SPI 事务 = header + payload + response
  · header   命令类别与长度
  · payload  命令与参数
  · response 执行结果，主控轮询读取

SPI 的关键差异在调度：它有自己的命令事件与线程，不占用 UART/I2C 共用的命令事件入口。

注意：调度独立，解析不独立——SPI 处理线程最终仍进入共享解析器，忙态与串行化规则不变。

5三通道对比与选型

选型先看宿主生态与带宽，再看帧复杂度：解析器始终唯一，帧与调度的差异都在入口侧。

通道帧结构调度典型主机适用
UART同步字 / 长度 / payload / 校验共享命令事件PC / 上位机调试、升级、通用控制
I2C（命令信箱）从机地址 + 寄存器信箱共享命令事件传感器侧主控短命令、状态位交接
SPIheader + payload + response独立 IO/Proc 线程板级主控批量命令、低延迟
结论：I2C 适合寄存器级小命令，UART 适合通用控制与日志，SPI 适合批量与低延迟；无论选哪条，命令都在同一个解析器里串行执行，结果沿原物理链路返回。

一句话总结

UART、I2C、SPI 三条物理通道分别服务不同宿主生态，帧格式与调度方式各异，但都收敛到同一个共享命令解析器——入口多样化、执行串行化，结果沿原物理链路返回。
