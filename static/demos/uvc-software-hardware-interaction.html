UVC 视频设备的软硬件分层架构：命令、数据与事件如何穿越四层

一台 UVC 视频设备的一头是 Windows 主机，另一头是红外图像硬件。命令从控制端点进、像素从 USB 端点出、硬件状态经中断回流——它们如何在一台固件设备里分四层穿越？本文按 PC / 固件 / 驱动 / 硬件逐层拆解，每个章节配一个交互动画，讲清机制后直接演示。

1四层职责：PC / 固件 / 驱动 / 硬件

一台 UVC 视频设备按职责切成四层：PC 侧是枚举与采集的 UVC 主机；固件业务层由应用与服务组成，负责业务决策与生命周期；驱动 / HAL 层把语义配置翻译成寄存器操作并初筛中断；硬件层是像素流水线与 USB 物理接口。四层各做一件事，命令、数据、事件在它们之间按固定方向行走。

层代表职责
PC / WindowsUVC 主机、厂商控制工具枚举、协商、采集；控制入口与采集终端
固件应用与服务相机应用、流管理、UVC Class、输出接口业务决策、参数解析、生命周期管理
驱动 / HALUSB Device Core、传输层、打包器驱动、ISR寄存器翻译、端点配置、中断初筛
硬件 IPISP、源流路由、UVC 打包器、端点 FIFO / PHY像素搬运、UVC 组帧、物理传输
三种颜色的通道：命令（蓝）从 PC 进控制面；数据（绿）由硬件单向流向 PC；事件（黄）从硬件经驱动回固件。全文动画用这三种颜色区分流动方向。

2命令通道：Probe / Commit 与私有控制

命令面负责协商与控制，走 EP0 控制端点。标准 UVC 用 Probe / Commit 协商视频参数；厂商工具用 Vendor 请求控制红外业务。两条命令通道都不经过视频数据端点。

通道入口载荷结果
Probe / CommitWindows UVC 栈 → EP0格式、帧索引、帧率、payload初始化打包器并按流类型启动
私有 Vendor 控制厂商工具 → EP0业务模式、测温、调色板、增益进消息队列，共享解析器处理，结果原路返回
注意：Vendor EP0 不通过 0x81 / 0x82 视频端点；命令返回成功不等于视频帧完整——二者是独立的观察点。

3数据通道：像素 → 打包器 → 端点 FIFO → PC

数据面是硬件单向流水线：ISP / Video 处理红外像素，源流路由选择源流，UVC 打包器（WRAPE）加上 UVC 头（Header / PTS / SCR / EOF）后直写端点 FIFO，USB 控制器再分包发送到 Windows。全程无 CPU 逐像素参与。

  • ISP / Video：红外校正与像素流水线
  • 源流路由（Stream SEL / USB TOP）：源流选择与帧控
  • UVC 打包器（WRAPE）：Header / PTS / SCR / EOF
  • EP FIFO / PHY：Bulk IN 0x81 / 0x82
直写边界：打包器到端点 FIFO 是直写；Windows 内核与用户态之间仍可能有自己的缓冲。固件管理生命周期，不逐帧复制 payload。

4事件回流：中断 / 回调

硬件状态不会自己走进固件，而是经中断 + 回调回流。打包器产生中断标志，ISR 清标志、映射事件、触发接收回调；UVC 服务线程在事件上下文中统计溢出、执行静止图像回调或唤醒停流等待者。

  • 中断用于状态反馈、统计、回调和停流同步
  • ISR 解析溢出 / 静止图像 / 帧空闲 / 帧起始 / 帧率变化等状态标志
  • 事件只做通知，不自动恢复流状态机
注意：上位机不会直接收到芯片的中断；一切硬件状态都要经驱动转换成事件后，固件线程才可见。

5边界与实现现状

架构之外，实现现状决定行为边界。几条已知边界值得记住：

边界现状
Commit 与流管理Probe/Commit 参数处理不调用流管理器，由相机启动流程按流类型分支
流类型分支非 MJPEG 直接启动 S0；MJPEG 走 JPEG 输出链；TPD 走 S1
接口生命周期GET / SET_INTERFACE 待实现
事件恢复打包器事件不自动恢复流状态机
三个独立观察点：命令成功、流处于运行态、接收端看到完整帧——它们各不相同，验证时要分开观察。

一句话总结

UVC 设备按 PC / 固件 / 驱动 / 硬件四层分工，命令走 EP0 控制面、像素走硬件单向数据面、状态经中断回流——控制、数据、事件三条通道边界清晰，行为由流类型分支与待办边界共同决定。
